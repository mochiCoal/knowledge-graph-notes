## 一、总体结论

这是一份完成度明显高于一般课程设计的工程：分层清晰（命令层 / 模型层 / store / service / view），Rust 端有 79 个单元测试，边界情况处理（成环树、孤儿节点、重复关联、导入包校验、恢复前安全副本、关闭前保存）考虑得比较充分；前端也做了路由懒加载、vendor 分包、空闲预取、确定性图谱布局等性能优化。

当前主要短板集中在四个方面：

1. **数据访问缺少统一策略**：每个命令新开连接、未启用 WAL、迁移只能幂等重放、关键唯一约束和索引依赖应用层。
2. **大数据量下的查询退化**：列表与搜索使用 `LIKE '%keyword%'` 全表扫描，摘要按行读取整篇正文，部分查询存在 N+1。
3. **前端状态与组件结构**：多个 store 各自维护同一份目录数据，靠页面 `mounted` 手动刷新；12 处重复的错误转换函数；单文件最大 1329 行。
4. **工程化缺口**：无 ESLint / Prettier / rustfmt / clippy 配置、无 CI；`.vs/` 与 14 MB 的 `src-tauri/kgn.exe` 被 Git 跟踪；前端测试只覆盖 utils。

## 三、分模块改进建议

### 3.1 数据访问与迁移层

**现状**

- `db::get_connection()` 为每次调用打开新连接，仅执行 `PRAGMA foreign_keys = ON; busy_timeout = 5000`（`db/mod.rs:28-41`）。所有 50 余个命令都走这条路径（如 `course.rs:82`、`note.rs:313`、`relation.rs:1224`）。
- 未设置 `journal_mode`，即默认 `DELETE` 日志模式；`backup.rs:188-199` 却按 WAL 的 `-wal/-shm` 做清理（本身无害，但说明设计意图与实际配置不一致）。
- 迁移是两个 `include_str!` 脚本的顺序 `execute_batch`，全部使用 `CREATE ... IF NOT EXISTS` / `INSERT OR IGNORE`，每次启动重放（`db/mod.rs:79-102`），没有版本表或 `PRAGMA user_version`。
- 约束现状：
  - `courses.name` 仅有应用层 `COLLATE NOCASE` 查重（`course.rs:57-77`），表上没有唯一索引；
  - `tags.name` 是表级 `UNIQUE`，但默认区分大小写；应用层却用 `COLLATE NOCASE` 判重（`tag.rs:50-81`），语义不一致；
  - `notes.knowledge_point_id` 没有唯一约束（`001_initial.sql`），而 `get_note` 用 `ORDER BY updated_at DESC LIMIT 1` 假设“一个知识点一条笔记”（`note.rs:291-299`）。
- 索引现状：知识点 `course_id`/`parent_id`、笔记 `knowledge_point_id`、关联 `source_id`/`target_id`、建议 `source_id`/`target_id`/`status` 已有；缺少 `notes(updated_at)`、`knowledge_relations(relation_type)`、`courses(name COLLATE NOCASE)`、`tags(name COLLATE NOCASE)` 等排序/过滤所需索引。

**问题**

1. 每次打开连接都有文件与 PRAGMA 开销；多连接并发写时锁竞争明显，`busy_timeout` 只能缓解、不能消除。
2. 只能重放幂等迁移，未来需要 `ALTER TABLE`、加约束、回填数据时非常受限，也无法判断“这个备份来自哪个 schema 版本”。
3. 关键唯一性缺失，导入课程包、并发保存或异常重试可能产生重复行；`tags` 的大小写唯一性只在应用层保证，绕过命令层就会失效。
4. 列表排序（`notes.updated_at`）和按类型筛选关联没有索引，数据量增大后退化为全表扫描 + 临时排序。

**改进方向**

1. **统一连接管理**：用 `tauri::State` 持有数据库句柄。
   - 方案 A（改动小）：`Mutex<Connection>` 单连接，所有命令串行执行，适合单机小数据量；
   - 方案 B（推荐）：`deadpool-sqlite` / `r2d2_sqlite` 读连接池 + 单独写连接（SQLite 单写多读），配合 WAL。
2. **启用 WAL**，与现有备份逻辑天然兼容：

```rust
conn.execute_batch(
    "PRAGMA journal_mode = WAL;
     PRAGMA synchronous = NORMAL;
     PRAGMA foreign_keys = ON;
     PRAGMA busy_timeout = 5000;
     PRAGMA temp_store = MEMORY;",
)?;
```

   退出或空闲时执行 `PRAGMA optimize;`（或每天一次），定期 `ANALYZE`。
3. **迁移版本化**：新增 `app_meta` 表或使用 `PRAGMA user_version`：

```sql
CREATE TABLE IF NOT EXISTS app_meta (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

   启动流程改为：读取版本 → 若低于当前，先在 `app_data_dir/backups` 生成自动备份 → 在事务中逐个执行未应用的迁移 → 写入新版本。迁移只前滚、不改历史脚本。
4. **迁移 003（一致性补丁）**：先合并/清理重复数据，再建唯一索引。示例：

```sql
-- 1) 每个知识点保留一条笔记：保留正文更长、更新时间更晚者
--    执行前必须自动备份；如需保留全部历史，应先迁移到 note_revisions 表
DELETE FROM notes
WHERE rowid NOT IN (
  SELECT rowid FROM (
    SELECT rowid,
           ROW_NUMBER() OVER (
             PARTITION BY knowledge_point_id
             ORDER BY length(content) DESC, updated_at DESC, rowid DESC
           ) AS rn
    FROM notes
  )
  WHERE rn = 1
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_notes_knowledge ON notes(knowledge_point_id);
CREATE UNIQUE INDEX IF NOT EXISTS uq_courses_name ON courses(name COLLATE NOCASE);
CREATE UNIQUE INDEX IF NOT EXISTS uq_tags_name ON tags(name COLLATE NOCASE);
CREATE INDEX IF NOT EXISTS idx_notes_updated ON notes(updated_at DESC);
CREATE INDEX IF NOT EXISTS idx_relation_type ON knowledge_relations(relation_type);
CREATE INDEX IF NOT EXISTS idx_suggestion_status_score
  ON relation_suggestions(status, score DESC);
```

   > 注意（唯一索引）：`courses.name` 与 `tags.name` 在历史数据中都可能存在仅大小写不同的重复值，直接 `CREATE UNIQUE INDEX ... COLLATE NOCASE` 会失败。迁移脚本应先按 `COLLATE NOCASE` 分组找出重复，把 `note_tags` 合并到保留记录，再建索引。
   >
   > 注意（重复笔记）：上面的 `DELETE` 会级联删除被删笔记的 `note_tags` 关联，且只保留一条正文。执行前必须自动备份；更稳妥的做法是先把重复笔记的正文与标签合并到保留记录（例如按段落拼接、标签取并集），再删除，避免静默丢内容。

5. **写操作事务化**：单语句写入本身是原子的，但跨语句组合（例如“创建标签 + 关联笔记”）应在同一个命令内完成并包在事务里，避免前端分两步调用造成半完成状态。建议把 `addTagToNote` 收敛为后端命令 `attach_tag_by_name(note_id, name)`。

**验收标准**

- 50 个并发保存请求无 `database is locked`，UI 不阻塞；
- 旧版本数据库（仅 001/002）可自动升级到 003，重复笔记数为 0，标签大小写重复数为 0；
- `EXPLAIN QUERY PLAN` 显示列表、按类型筛选、同名查重均命中索引；
- `PRAGMA integrity_check` 通过。

### 3.2 Rust 命令层与错误模型

**现状**

- 所有命令返回 `Result<T, String>`，错误信息为中文展示串（如 `course.rs:98`、`relation.rs:1162`）。
- 命令均为同步 `pub fn`，第一行 `get_connection(&app)`；备份/恢复中的 `VACUUM INTO`、文件复制也在同步命令内完成（`backup.rs:205-240`、`262-317`）。
- `lib.rs` 仍注册调试命令 `greet`（`lib.rs:7-10, 23`）；除 `initialize_database` 的 `println!`（`db/mod.rs:99`）外无日志。
- 明显的重复查询/N+1：
  - `load_detail` 对子树每个节点各执行一次 `count_notes`（`knowledge_point.rs:350-354`）；
  - `delete_point` 对子树逐条 `DELETE`、删除前再逐条统计笔记（`knowledge_point.rs:518-548`）；
  - `attach_tag_names` 把整张 `note_tags` + `tags` 拉进内存再按 ID 过滤（`note.rs:81-117`）；
  - `list_tag_summaries` 用相关子查询为每个标签统计笔记数（`tag.rs:95-127`）。
- `relation.rs` 约 1800 行，同时包含关联 CRUD、关联类型字典、建议算法与分词，职责过重。

**问题**

1. 错误不可判别：前端只能展示字符串，无法实现“冲突时重试”“未找到时跳转”“校验错误定位到字段”等差异化处理。
2. 同步命令运行在 Tauri 的 IPC 处理线程上；长时间查询、`VACUUM`、文件复制会阻塞该线程，造成界面无响应（尤其恢复大数据库时）。
3. N+1 查询与全表拉取在数据量增长后成本线性甚至平方增长。
4. 无持久化日志，用户报错只能截图，难以定位数据库、路径与版本信息。

**改进方向**

1. **统一错误类型**：用 `thiserror` 定义可序列化的 `AppError`，带稳定的 `code`：

```rust
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error("{0}")]
    Validation(String),
    #[error("{0}")]
    NotFound(String),
    #[error("{0}")]
    Conflict(String),
    #[error("数据库操作失败：{0}")]
    Database(#[from] rusqlite::Error),
    #[error("IO 操作失败：{0}")]
    Io(#[from] std::io::Error),
    #[error("内部错误：{0}")]
    Internal(String),
}

impl AppError {
    pub fn code(&self) -> &'static str {
        match self {
            Self::Validation(_) => "VALIDATION",
            Self::NotFound(_) => "NOT_FOUND",
            Self::Conflict(_) => "CONFLICT",
            Self::Database(_) => "DATABASE",
            Self::Io(_) => "IO",
            Self::Internal(_) => "INTERNAL",
        }
    }
}

impl serde::Serialize for AppError {
    fn serialize<S: serde::Serializer>(&self, serializer: S) -> Result<S::Ok, S::Error> {
        use serde::ser::SerializeStruct;
        let mut state = serializer.serialize_struct("AppError", 2)?;
        state.serialize_field("code", self.code())?;
        state.serialize_field("message", &self.to_string())?;
        state.end()
    }
}
```

   前端 `CommandError` 增加 `code` 字段（`services/tauri.ts:9-17`），便于统一处理；SQLite 的 `UNIQUE constraint failed` 映射为 `Conflict`。

2. **长任务异步化**：

```rust
#[tauri::command]
pub async fn backup_database(
    app: tauri::AppHandle,
    destination: String,
) -> Result<BackupResult, AppError> {
    tauri::async_runtime::spawn_blocking(move || {
        let conn = db::get_connection(&app)?;
        backup::backup_to(&conn, &PathBuf::from(destination))
            .map_err(AppError::Internal)
    })
    .await
    .map_err(|e| AppError::Internal(format!("备份任务异常终止：{e}")))?
}
```

   对纯查询同样适用；短小命令可保留同步，避免过度改造。

3. **消除 N+1**：用递归 CTE 取子树，用一条 `GROUP BY` 统计笔记数：

```sql
WITH RECURSIVE subtree(id) AS (
  SELECT id FROM knowledge_points WHERE id = ?1
  UNION ALL
  SELECT kp.id
  FROM knowledge_points kp
  JOIN subtree s ON kp.parent_id = s.id
)
SELECT kp.id, COUNT(n.id) AS note_count
FROM subtree s
JOIN knowledge_points kp ON kp.id = s.id
LEFT JOIN notes n ON n.knowledge_point_id = kp.id
GROUP BY kp.id;
```

   删除时先收集 ID，再用临时表或 `IN` 批量删除；统计笔记数用 `WHERE knowledge_point_id IN (...)` 一次完成。

4. **标签批量查询**：`attach_tag_names` 改为按摘要 ID 批量 `IN` 查询（或先把 ID 写入临时表再 JOIN），避免全表拉取。

5. **拆分 `relation.rs`**：`relation/` 目录下拆为 `crud.rs`、`types.rs`、`suggestion.rs`、`similarity.rs`，纯算法（分词/余弦/Jaccard）独立便于基准测试。

6. **日志与调试**：接入 `tauri-plugin-log`（滚动文件写入 `app_log_dir`），移除 `greet`，在关键写操作与备份/恢复处记录结构化日志；release 下 `panic = "abort"` 建议配合 `std::panic::set_hook` 至少写入日志文件。

**验收标准**

- 前端可基于 `error.code` 做分支处理；用户看到的文案保持中文友好；
- 备份/恢复期间 UI 可交互（有 busy 状态即可）；
- 删除 1000 节点子树时 SQL 语句数 < 10（可用 rusqlite 的 `trace` 或日志计数验证）；
- `cargo clippy -- -D warnings` 通过。

### 3.3 搜索

**现状**

- 笔记列表与搜索：`n.title LIKE ? OR n.content LIKE ?`，`ESCAPE '\'`，标题命中优先排序（`note.rs:131-158`）。
- 全局搜索：课程/知识点/笔记/标签/关联五组 `LIKE`，每组固定 `LIMIT`（6 / 12 / 12 / 8 / 8，`search.rs:10-14, 289-315`）。
- 列表摘要处，逐行读出完整 `content` 后计算 `excerpt` 与 `character_count`（`note.rs:44-60`）。

**问题**

1. `%keyword%` 无法使用 B-tree 索引，必然全表扫描；笔记正文越长、条数越多，成本越高。
2. 列表页每次刷新都要把全部正文从 SQLite 读到 Rust 再清洗、截断、统计，属于重复计算。
3. `search_notes` 与 `list_notes` 返回全部结果，没有分页/总数；笔记库一次性渲染所有卡片。
4. 全局搜索固定上限导致“结果被截断但没有查看全部入口”。

**改进方向**

1. **物化派生字段（性价比最高）**：迁移 004 为 `notes` 增加：

```sql
ALTER TABLE notes ADD COLUMN excerpt TEXT NOT NULL DEFAULT '';
ALTER TABLE notes ADD COLUMN character_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE notes ADD COLUMN plain_text TEXT NOT NULL DEFAULT '';
```

   `save_note` 与 `read_markdown_file`/导入时一次性计算并写入；`NOTE_SUMMARY_SELECT` 不再选择 `n.content`。历史数据在迁移中回填（分批 `UPDATE ... WHERE plain_text = ''`）。

2. **FTS5 全文索引**：为 `title`、`plain_text` 建虚表，触发器同步：

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS note_fts USING fts5(
  title,
  body,
  content='notes',
  content_rowid='rowid',
  tokenize='unicode61'
);
```

   中文检索策略二选一：
   - **bigram 预处理**：写入与查询都把连续 CJK 串切成二元组（`链表` → `链表` / 也可切单字+双字），查询用 `phrase` 保证顺序；实现可复用 `relation.rs:608-661` 的分词思路；
   - **trigram tokenizer**：`tokenize='trigram'` 支持子串匹配，但要求查询至少 3 个字符，2 字中文需回退到 bigram 索引或 `LIKE` 兜底。
   建议将 FTS 与 `LIKE` 组合：FTS 取候选集，再对少量候选做精确过滤与高亮。
   > 需确认 `rusqlite` 的 `bundled` 特性是否已启用 FTS5；若没有，改用 `bundled-full` 或显式开启 `SQLITE_ENABLE_FTS5`，并在 CI 中加一条 FTS 冒烟测试。

3. **分页 + 虚拟滚动**：新增 `list_notes_page(page, page_size, tag_id)` 返回 `{ items, total }`；前端笔记库改为分页或虚拟列表（`useVirtualList`），首屏只渲染 20~50 条。

4. **统一搜索接口**：`search(query, { kinds, limit, offset })`，返回 `total` 与 `has_more`；搜索面板支持“查看全部笔记”跳转到笔记库并带入关键词。

5. **搜索片段**：用 FTS5 `snippet()` 返回命中片段与位置，前端高亮，避免把整篇正文传到前端。

**验收标准**

- 1 万条笔记（平均 5 KB）下：列表首屏查询 < 200 ms，搜索 < 300 ms；
- 2 字中文关键词可命中（如“链表”“索引”）；
- 列表查询不再读取 `notes.content`（可用 `EXPLAIN QUERY PLAN` 与 SQL 日志验证）。

### 3.4 关联建议

**现状**

- `generate_suggestions` 每次对同课程所有候选重新分词、打分（`relation.rs:1062-1156`），笔记文本一次性全量载入（`load_note_texts`，`relation.rs:872-917`）。
- 前端每次切换知识点都会调用（`stores/notes.ts:278, 320-340`），后端随即删除旧的 `pending` 建议并插入新建议（`relation.rs:1117-1150`）。
- 相似度权重固定为 0.45/0.25/0.20/0.10（`relation.rs:780-783`），阈值与上限为常量；分词为 CJK bigram + 英文单词，无 IDF。

**问题**

1. 切换知识点即触发一次“全课程候选 × 全文分词 + 写库”，属于高频写放大；用户只是浏览也会产生大量 `DELETE/INSERT`。
2. 常见词（“数据”“结构”）在所有候选里权重相同，容易产生噪声建议。
3. 建议无过期策略，`pending` 记录会持续累积。
4. 算法与 CRUD 混在同一文件，难以基准与调参。

**改进方向**

1. **按需触发**：默认只在用户点击“重新推荐”时生成；或改为空闲任务（前端 `requestIdleCallback` / 后端异步），切换知识点时只读取已保存的建议。
2. **缓存与增量**：为每个知识点维护 `content_hash`（title + description + 笔记 updated_at + 字符数）与已算好的词向量；仅当哈希变化时重算。可用进程内 LRU 或表 `point_terms(point_id, terms_json, updated_at)`。
3. **IDF 加权与停用词**：统计课程内文档频率，降低高频词权重；阈值从 `MIN_SUGGESTION_SCORE` 移到配置（数据库 `settings` 表或 `app_meta`），便于调参。
4. **候选预筛**：先用标题 bigram 交集、标签交集、同层/相邻层级缩小候选，再做全文相似度。
5. **TTL 与清理**：`relation_suggestions` 增加 `expires_at`；启动时清理过期 `pending`；已接受/拒绝记录保留用于去重。
6. **算法模块化 + 基准**：把 `tokenize/cosine/jaccard/score_candidate` 移到 `suggestion/similarity.rs`，加 `criterion` 基准（1k/10k 候选）。

**验收标准**

- 切换知识点不再产生数据库写入（只有显式生成时写入）；
- 1000 个候选的生成耗时 < 500 ms（异步执行，不阻塞 UI）；
- 建议结果中高频泛词占比明显下降（可用固定语料回归测试对比）。

### 3.5 备份与恢复

**现状**

- 备份使用 `VACUUM INTO` 写临时文件 → `quick_check` 校验 → 重命名替换，失败清理临时文件（`backup.rs:205-240`），设计良好。
- 恢复前创建 `knowledge_graph-before-restore-*.db` 安全副本（`backup.rs:243-259`），替换失败尝试回滚（`backup.rs:301-317`）。
- 恢复命令完成后重放迁移（`backup.rs:356-379`）；设置页 1.8 s 后 `window.location.reload()`（`SettingsView.vue:125-150`）。

**问题**

1. 只有手动备份：没有启动/退出自动备份，也没有保留份数策略，用户误删数据库后可能无备份可用。
2. 备份文件无元数据（schema 版本、应用版本），恢复前无法判断兼容性；旧备份依赖幂等重放补齐，未来破坏性迁移会失败。
3. 恢复是同步命令，数据库较大时 UI 冻结且无进度反馈；恢复前的草稿 flush 依赖路由卸载的异步调用，存在竞态。
4. 无单实例：第二个进程可能在恢复过程中仍持有旧数据库文件（Windows 下可能直接导致替换失败）。
5. 整页 `reload` 简单可靠，但会丢失所有未持久化的 UI 状态（筛选、滚动、面板布局）。

**改进方向**

1. **自动备份**：启动成功后检查 `app_data_dir/backups` 中最近备份时间，超过 24 小时则生成一份；保留最近 7 份，按时间命名；退出时可选备份。
2. **备份元数据与版本校验**：在备份副本中写入 `app_meta`（`schema_version`、`app_version`、`created_at`）；或同名 `.json` 校验文件。恢复前比较 `schema_version`，高于当前应用支持版本时拒绝并提示升级应用。
3. **恢复流程标准化**：

```text
用户确认 → 前端 flushSave()（等待完成）
        → 禁用写操作 / 显示进度 → 后端创建安全副本
        → 关闭连接池 → 替换文件 → 迁移 → 重建连接池
        → 通过事件通知前端刷新 store（或受控 reload）
```

4. **进度事件**：备份/恢复用 `app.emit("backup://progress", { phase, percent })`，前端显示进度条。
5. **单实例**：`tauri-plugin-single-instance`，第二次启动时聚焦已有窗口，避免并发恢复/写入。

**验收标准**

- 恢复失败时数据库与恢复前完全一致（哈希一致），安全副本可用；
- 备份文件可在“未来版本”中被识别并拒绝恢复；
- 数百 MB 至 1 GB 的数据库备份/恢复期间窗口仍可拖动、有进度显示；
- 双开应用时第二个实例不会打开数据库。

```ts
// src/utils/error.ts
export function toErrorMessage(error: unknown): string {
  if (typeof error === 'string') return error
  if (error instanceof Error) return error.message
  return String(error)
}
```

```ts
// src/composables/useAsyncTask.ts
export function useAsyncTask<T>(task: () => Promise<T>) {
  const loading = ref(false)
  const error = ref<string | null>(null)
  let requestId = 0

  async function run(): Promise<T | undefined> {
    const current = ++requestId
    loading.value = true
    error.value = null
    try {
      const result = await task()
      return current === requestId ? result : undefined
    } catch (e) {
      if (current === requestId) error.value = toErrorMessage(e)
      return undefined
    } finally {
      if (current === requestId) loading.value = false
    }
  }

  return { loading, error, run }
}
```

3. **存储访问统一**：`utils/storage.ts` 提供带命名空间、JSON 序列化与异常保护的 `readStorage/writeStorage`，替换散落的 `localStorage` 调用（`theme.ts`、`app.ts`、`workspace.ts`、`notes.ts`）。
4. **类型生成**：用 `ts-rs` 从 Rust 模型导出 TypeScript 类型（构建时生成 `src/types/generated.ts`），或在 CI 中对比两端结构；至少为命令参数建立共享常量。
5. **按领域拆 store**：`notes` 只保留“当前笔记 + 草稿 + 保存状态”，标签、建议、目录分别独立；降低单文件复杂度到 200 行以内。

**验收标准**

### 3.8 笔记编辑器与自动保存

**现状**

- 保存设计较完善：800 ms 防抖、`saveTask` 串行化、切换知识点前 `flushSave()`、保存期间继续输入保持 `dirty`（`stores/notes.ts:379-448`）。
- 关闭窗口时拦截 `onCloseRequested` 并 `flushSave()`（`TitleBar.vue:70-82`）。
- `saveStatus` 状态：`idle | dirty | saving | saved | error`。
- 预览用 computed 每次输入重新渲染整篇 Markdown（`NoteWorkspace.vue:40`）。
- Markdown 导入有大小限制（2 MB）、编码校验与覆盖提示（`note.rs:17, 218-278`）。

**问题**

1. **保存失败后关闭窗口仍销毁**：`TitleBar.vue:70-82` 中 `await notesStore.flushSave()` 的返回值被忽略，`finally` 里直接 `destroy()`。若保存失败（磁盘满、数据库锁、路径问题），用户会在不知情中关窗，最后一段内容丢失。
2. **error 状态不会自动恢复**：`scheduleSave` 只在输入或手动保存时触发；进入 `error` 后如果没有继续输入，笔记会一直停留在未保存状态，没有退避重试。
3. **全量保存**：每次自动保存都通过 IPC 传输整篇正文、执行整行 UPDATE；长文档（数百 KB）会有明显拷贝与写放大，且 `save_note` 返回完整 `Note`（包含 content）再经 IPC 回传。
4. **无冲突检测**：`UPDATE notes ... WHERE id = ?` 不校验版本；多窗口（若未来支持）或多实例会静默覆盖。
5. **离开页面的 flush 不等待**：`NotesView.vue:57` 使用 `void notes.flushSave()`，组件卸载后请求仍在继续（store 常驻，通常能完成），但无法向用户反馈失败。
6. **预览性能**：长文档每次按键都重新解析整篇 Markdown 并替换 `v-html`，输入延迟随文档长度增长。

**改进方向**

1. **关闭保护**（P0）：

```ts
const stopClose = await appWindow.onCloseRequested(async (event) => {
  if (isClosing.value) return
  event.preventDefault()
  isClosing.value = true

  const saved = await notesStore.flushSave()
  if (!saved) {
    isClosing.value = false
    // 弹出“保存失败：重试 / 导出副本 / 放弃修改并退出”
    return
  }

  await appWindow.destroy()
})
```

2. **显式状态机与重试**：状态扩展为 `idle | dirty | saving | saved | error | conflict`；`error` 后按 1s/2s/4s 退避自动重试（最多 3 次），并在界面上提供“重试/复制正文”操作。
3. **精简保存返回**：`save_note` 返回 `{ id, updated_at, character_count }`，前端用它更新状态即可，不需要回传整篇正文。
4. **乐观锁**：请求携带 `base_updated_at`，SQL 改为：

```sql
UPDATE notes
SET title = ?1, content = ?2, updated_at = ?3, version = version + 1
WHERE id = ?4 AND version = ?5;
```

   受影响行数为 0 时返回 `Conflict`，前端提示“该笔记已在别处修改”，提供对比/覆盖选项。
5. **增量或降频保存**：对超大文档（如 > 100 KB）降低自动保存频率到 1.5~2 s，或按段落 diff 只提交变化片段（可作为后续优化）。
6. **预览防抖**：`renderedContent` 改为 `watch(draft.content)` + 150 ms 防抖（或 `requestIdleCallback`），并且只在预览可见时渲染；滚动同步用 `requestAnimationFrame` 节流（当前每次 scroll 事件直接计算，`NoteWorkspace.vue:75-82`）。
7. **导出兜底**：保存失败横幅中提供“导出当前草稿到 .md”，避免用户被卡死。

**验收标准**

- 模拟保存失败时关闭窗口，窗口不关闭且有明确提示；
- 断网/磁盘满恢复后，草稿自动重试成功；
- 多实例并发保存同一笔记时第二次保存得到冲突提示，不静默覆盖；
- 100 KB 文档输入无可感知卡顿（预览防抖生效）。

### 3.9 知识图谱

**现状**

- 层次布局：紧凑树形放置 + 重心排序，确定性输出（`utils/graphLayout.ts:89-186`）。
- 力导向：以层次布局为初值，两两库仑排斥 + 矩形碰撞 + 24 轮重叠分离（`graphLayout.ts:222-380`）。
- 画布开启 `only-render-visible-elements`、关掉双击缩放、只显示一跳边标签（`GraphCanvas.vue:372-390`）。
- `points` 或 `layout` 变化时整体重建节点与边；`relations` 变化只更新计数与连线（`GraphCanvas.vue:320-361`）。

**问题**

1. **O(n²) 主线程计算**：力导向每轮两两计算，160 节点 × 140 轮约 180 万次距离计算；500 节点约 1700 万次，叠加 24 轮重叠分离，容易出现数百毫秒到数秒的卡顿，期间界面无响应。
2. **重建丢失拖拽位置**：`points` 变化（切换课程、筛选层级、刷新）会重新布局，用户手动摆放的节点位置被覆盖；位置没有持久化。
3. 大图缺少折叠/聚合与层级展开策略；深层树铺开后画布非常宽，`fitView` 后文字过小。
4. 布局为同步函数，无法取消；快速切换课程时可能连续计算多次。
5. 可访问性弱：节点只能鼠标点击，键盘用户无法遍历图谱；详情面板与画布的焦点关系不明确。

**改进方向**

1. **布局移入 Web Worker**：把 `layoutHierarchy` / `layoutForce` 作为纯函数放入 `graphLayout.worker.ts`，主线程只接收结果；切换课程时取消上一次任务（`taskId` 比对）。
2. **降低复杂度**：节点数 > 200 时使用 Barnes-Hut 近似（四叉树）或网格分桶；重叠分离限制迭代轮数并对大图跳过（或使用空间哈希）。
3. **位置持久化**：
   - 轻量：`localStorage` 按 `courseId` 存 `{ pointId: {x,y} }`，配合“重新布局”按钮清除；
   - 可靠：新增 `graph_layout(course_id, point_id, x, y, updated_at)` 表，跨设备/重装保留（需评估是否必要）。
4. **增量更新**：`relations` 或选中态变化时不重建节点；节点拖拽结束记录位置；筛选只改变可见集合，不重置其余节点坐标。
5. **大图体验**：支持折叠子树（点击节点折叠/展开）、按层级分批展开、缩放级别 LOD（低缩放只画节点轮廓）、图例与边类型开关（已有类型筛选）。
6. **可访问性**：提供“列表视图”作为图谱的等价入口（已有知识点树可复用）；画布节点加 `tabindex` 与 `aria-label`，Enter 选中、方向键移动焦点。

**验收标准**

- 500 节点力导向布局耗时 < 800 ms 且不阻塞 UI（Worker）；
- 拖拽 10 个节点后切换筛选，位置保持不变；
- 关闭再打开同一课程，节点位置恢复（若启用持久化）；
- 布局算法有基准测试（100/500/1000 节点）。

### 3.11 性能与包体积

**已有优势**

- 路由懒加载、`manualChunks` 拆分 `vue` / `graph` / `markdown`（`vite.config.ts:20-36`）；
- 首屏后空闲预取其它页面（`main.ts:13`、`router/prefetch.ts`）；
- 图谱 `only-render-visible-elements`、边标签默认关闭；
- 后端列表查询避免加载全文（`NoteSummary` 不含 content，设计意图正确）。

**可改进点**

1. **列表虚拟化 / 分页**：`NoteLibraryView` 与 `TagsView` 一次性渲染全部条目；笔记达到数百条后，DOM 与筛选计算都会变慢。建议分页（后端）+ 虚拟滚动（前端）。
2. **响应式开销**：`stores/notes.ts` 的 `knowledgePoints`、`relations`、`allTags` 使用 `ref<Array>`，Vue 会对每个对象做深度代理；数据量大时（数千节点/关联）有明显的初始化与更新成本。只读的大型集合建议 `shallowRef` + 整体替换：

```ts
const knowledgePoints = shallowRef<KnowledgePoint[]>([])
// 更新时整体替换，避免深层响应式代理
knowledgePoints.value = [...knowledgePoints.value, point]
```

3. **预览渲染节流**：见 3.8；另外 `v-html` 每次替换整块 DOM，长文档可考虑按标题分块渲染。
4. **图谱布局**：见 3.9；优先 Worker + 近似算法。
5. **数据库查询**：物化摘要（3.3）、批量标签查询（3.2）、索引补齐（3.1）。
6. **构建体积预算**：用 `rollup-plugin-visualizer` 生成报告，CI 中设阈值（例如主包 < 300 KB gzip、graph chunk < 250 KB gzip），防止无意引入大依赖。
7. **启动路径**：迁移当前每次启动重放两个 SQL 脚本（`db/mod.rs:91-102`）；改为版本表后仅在升级时执行，正常启动零迁移开销。首页统计可合并为一次查询（`TableCounts` 已合并）。
8. **动画与滚动**：图谱 `fitView` 动画 380 ms、详情面板过渡等，在低性能设备上可通过 `prefers-reduced-motion` 关闭。

**验收标准**

- 1000 条笔记的笔记库首屏渲染 < 500 ms；
- 500 节点图谱切换课程到可见 < 1 s，且不阻塞输入；
- 构建产物有体积报告并在 CI 中受控。

### C. 何时可以“不做”

以下优化在单机、个人使用、数据量不大（例如笔记 < 1000 条、知识点 < 500 个）时收益有限，可按需延后：

- 连接池、FTS5、Web Worker、虚拟滚动：可先用“阈值触发”策略（数据量超过阈值再启用）。
- 乐观锁与多窗口：若明确不支持多实例，单实例插件即可满足；但建议保留 `version` 字段，成本低、为未来留余地。
- i18n：若产品只面向中文用户，集中文案即可，不必引入完整 i18n 框架。
- 图谱位置持久化：若用户主要使用层次布局且不常拖拽，可延后。

判断标准建议写进项目文档：**以“用户可感知的卡顿/数据风险”为优先级依据，而不是以“技术上更先进”为依据。**

## 六、值得保留的设计

评审中也有不少值得保留并推广的做法：

1. **边界数据兜底**：树成环/孤儿节点不丢失（`knowledge_point.rs:206-290`）、布局成环保护（`graphLayout.ts:49-75`），并有对应测试。
2. **备份的临时文件 + 校验 + 重命名**：避免半截备份（`backup.rs:205-240`），失败清理。
3. **导入包校验与事务**：`course_transfer.rs` 有结构校验、名称去重、事务写入与往返测试。
4. **前端请求竞态处理**：`requestId` 丢弃旧响应，避免快速切换时的错乱。
5. **错误提示友好**：后端错误均为可读中文，前端直接展示；在此基础上再补 `code` 即可兼顾可读性与可编程处理。
6. **构建优化意识**：懒加载、分包、预取、`only-render-visible-elements`，说明作者对性能有主动思考。

这些设计是后续重构的良好基础，建议在拆分模块时保留其行为并用测试固化。
